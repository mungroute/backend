# D12 Redis presence 예비 부하 테스트

측정일: 2026-08-17  
환경: 로컬 Windows, Spring Boot + PostgreSQL + Redis 7.4.10, k6 2.2.0

## 합격 기준

- HTTP 실패율 1% 미만
- `presence.update` p95 300ms 미만
- `presence.update` p99 700ms 미만
- 성공 응답의 개인정보 계약 위반 0건

500 VU에서 기능 중단이나 k6 iteration 중단은 없었지만, HTTP 실패 170건과 긴 대기가 발생해 합격 기준을 넘었다. 최초 스크립트의 `privacy_contract_failed`는 HTTP 실패도 개인정보 실패로 집계했으므로 실제 개인정보 노출을 의미하지 않는다. 이후 스크립트에서 두 지표를 분리했다.

## 확인된 병목과 조치

기존 구현은 요청마다 GEO 후보 20명의 Redis 메타데이터를 개별 조회하고, 응답 상위 3명을 고르기 전에 모든 후보의 거리 이력도 개별 갱신했다. 요청 한 건에서 수십 회의 순차 Redis 왕복이 발생해 500 VU에서 서버 요청 스레드가 대기했다.

- GEO 후보 제한: 20명 → 6명
- 정확 거리 정렬 후 최종 3명에 대해서만 거리 이력 갱신
- HTTP 실패와 개인정보 계약 지표 분리

백엔드 전체 회귀 테스트를 통과했으며 아래와 같이 최적화 반영 후 500 VU를 재측정했다.

## 최적화 후 재측정

동일한 500개 고유 계정·세션 fixture로 재측정한 결과 HTTP 요청 18,687건과 검사 37,374건이 모두 성공했다. 중단 iteration과 개인정보 계약 위반은 모두 0건이다. p95는 6.33초에서 45.61ms로, p99는 7.59초에서 76.38ms로 감소했다. 로컬 D12 예비 합격 기준을 충족했으므로 1,000·2,500·5,000 VU와 WebSocket 알림 지연 측정은 D17 최종 부하 시험으로 넘긴다.

테스트 과정에서 `k6-presence-*` 이메일을 사용하는 로컬 테스트 계정과 활성 산책 세션이 생성됐다. 실제 서비스 데이터와 구분되며, 정리 작업은 별도 승인 후 수행한다.

## WebSocket 완료 검증

D12 최종 연결 구조는 STOMP WebSocket을 우선 사용하고, 연결 전·재연결 중·오류 발생 시
기존 REST `PUT /api/presence`로 자동 폴백한다.

- 연결: `GET /ws`, STOMP `CONNECT`의 Bearer JWT를 서버에서 검증
- 업로드: `SEND /app/presence`
- 개인 응답: `SUBSCRIBE /user/queue/presence`
- 재사용 로직: REST와 WebSocket 모두 동일한 `PresenceUpdateService` 판정 사용
- 종료 조건: 거리두기 OFF, 산책 일시정지·종료, 화면 이탈 시 소켓 종료
- 재연결: 5초 간격, 재연결 전까지 REST 위치 갱신 유지

실제 Spring Boot 서버와 k6를 사용한 1 VU 왕복 스모크 테스트에서 WebSocket handshake
101, 세션 일치, 개인정보 계약을 모두 통과했다. 연결부터 개인 응답 수신 및 종료까지의
세션 시간은 428.85ms였고 실패는 0건이었다. 백엔드 전체 테스트와 프론트 187개 테스트,
프론트 프로덕션 빌드도 모두 통과했다.
